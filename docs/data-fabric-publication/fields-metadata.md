# Fields

<https://documentation.neutrinos.com/articles/#!data-fabric-publication/fields-metadata>

This section outlines the fields included in the Fields sheet of the Excel workbook.

| **Field  ** | **  Description  ** | **  Naming Convention** |
| --- | --- | --- |
| ObjectAPIName | The ObjectAPIName field specifies the unique identifier assigned to an object. This identifier is used by APIs and integrations to reference the object programmatically. Select a value from the list of names populated from the Objects sheet. | Must be unique within the environment to avoid conflicts    Must be a string identifier without spaces. Underscores (_) to replace spaces or separate words.    Typically case-sensitive; best practice is to use camelCase or snake_case for readability. |
| FieldLabel | The FieldLabel defines the human-readable display name of a field within an object | Must be a string value written in natural language.    Allowed characters:    Alphabets, numbers, and spaces      Use Title Case (capitalize the first letter of each major word).    Keep it short    Avoid internal abbreviations or acronyms unless they are domain standard.    Ensure labels are unique within the object for clarity. |
| FieldAPIName | The FieldAPIName is the programmatic reference used by APIs, integrations, and automation workflows to identify and interact with the field. Unlike the FieldLabel (which is user-facing), the FieldAPIName functions as a technical key that ensures consistency and unambiguous referencing across processes. | Must be a string identifier without spaces.    Allowed characters:    Alphabets (A–Z, a–z)    Numbers (0–9)    Underscores (_) for separating words      Begin with a letter (not a number). |
| FieldType | The FieldType field defines the data type of a field within an object. It determines the kind of data that can be stored, how it is validated, displayed in the UI, and used in calculations, queries, or integrations. | Type: Enumerated string representing the field’s data type.Allowed values (common types in Data Fabric):string: Textual datanumber: Numeric data (includes both Integers and Floating point numbers)boolean: Date valuesdate: Date values |
| PII | The PII (Personally Identifiable Information) field indicates whether a field within an object contains sensitive data that can directly or indirectly identify an individual. Marking a field as PII is critical for data governance, security, and compliance with regulations such as GDPR, HIPAA, or India’s DPDP Act. | Boolean (Yes/No, True/False) or enumerated flag.    Allowed values:    true / false    yes / no (if system uses string-based flags) |
| GDPRPurpose | The GRPRPurpose field specifies the intended purpose for which data is collected, stored, or processed in compliance with data protection regulations (such as GDPR). It documents the lawful basis or justification for handling a particular field, helping organizations maintain data governance, transparency, and regulatory compliance. | Type: String (enumerated or controlled vocabulary recommended).    Allowed values: Must align with predefined GDPR purposes recognized by the organization, such as:    consent    contract    legal_obligation      Use lowercase letters.    Use underscores (_) to separate multiple words. |
| IsRelationship | The IsRelationship field indicates whether a given field functions as a relationship field between two objects. When set to true, the field does not merely hold data but establishes a link or reference to another object, enabling relational data modeling. | Type: Boolean (true / false).    Always use lowercase values. |
| RelationshipTargetObject | The RelationshipTargetObject field defines the object that serves as the target when a relationship is established through a field. It is used in conjunction with the IsRelationship attribute to specify which object the relationship points to. This field ensures that a relationship field correctly maps to the intended object. | Type: String.    Format: Must reference a valid ObjectAPIName of the target object.    Allowed characters:    Alphanumeric (A–Z, a–z, 0–9)    Underscores (_) |
| Cardinality | The Cardinality field specifies the nature of the relationship between two objects when a field is marked as a relationship (IsRelationship = true). It defines how many instances of one object can be associated with instances of another object. Cardinality is essential for data modeling, referential integrity, and query optimization | Type: String (enumerated).    Allowed values (predefined, controlled vocabulary):    one_to_one: Each record in the source object relates to exactly one record in the target object.    one_to_many: A single record in the source object can relate to multiple records in the target object.    many_to_one: Multiple records in the source object relate to a single record in the target object.    many_to_many: Multiple records in the source object relate to multiple records in the target object. |
| CascadeBehavior | The CascadeBehavior field defines how actions performed on a parent object (such as update or delete) should be propagated to related child objects when the field represents a relationship (IsRelationship = true). It controls the impact of parent operations on dependent records, ensuring consistency and preventing orphaned or unintended records. | Type: String (enumerated, controlled vocabulary).    Allowed values (standard options):    none: No cascading; child objects remain unaffected.    cascade_delete: Deleting the parent automatically deletes related child records.    cascade_update: Updating parent keys/identifiers automatically updates related child references.    restrict: Prevents deletion or update of the parent if related child records exist.    set_null: On parent deletion, child references are cleared (set to null).      Use lowercase letters.    Use underscores (_) to separate words. |
| HelpText | The HelpText field provides contextual guidance or instructions for end-users interacting with a specific field. It acts as a descriptive tooltip or inline note that explains the field’s purpose, usage, or input expectations. | Type: String (free-text).    Format:    Written in sentence case.    Should be clear, concise, and instructional.    Avoid overly technical jargon unless required for the audience.      Allowed characters:    Alphanumeric, spaces, and common punctuation (. , : - ( )). |
| ValueSetAPIName | The ValueSetAPIName field specifies the API identifier of a predefined value set that is associated with a field. | Type: String (identifier).    Format:    Must be a valid API name (similar to ObjectAPIName conventions).    No spaces allowed.    Use lowecase or camelCase consistently.    Use underscores ( _ ) to separate words if sname_case is preferred.      Allowed characters:    Alphabets (A-Z, a-z)    Numbers (0-9)    Underscores ( _ ) |
| UI_Widget | The UI_Widget field specifies the type of user interface control used to display or capture data for a specific field. It determines how end-users interact with the field in forms, dashboards, or reports. Selecting the appropriate UI widget ensures data accuracy, usability, and a consistent user experience. | Type: String (enumerated, controlled vocabulary).    Allowed values (commonly used widget types):    TextInput: Single-line text input    TextArea: Multi-line text input    Dropdown: Single-select picklist, and so on. |
| UI_Label | The UI_Label field specifies the display name of a field in the user interface. It is a user-facing label that appears in forms, dashboards, and reports, helping end-users understand the purpose of the field without referencing technical identifiers like FieldAPIName. | Type: String (user-friendly text).    Format:    Use Title Case (capitalize first letter of each major word).    Avoid technical jargon unless the audience is strictly technical.      Allowed characters:    Alphabets, numbers, spaces    Limited punctuation (- , . : ( )) if necessary |
| UI_Placeholder | The UI_Placeholder field provides a short, descriptive hint or example displayed inside a field in the user interface before the user enters a value. It helps guide end-users on expected input formats or content, improving usability and reducing data entry errors. | Type: String (user-facing text).Format:Short, concise, and action-oriented (e.g., “Enter email address”).Written in sentence case for readability.Allowed characters:Alphabets, numbers, spacesCommon punctuation (. , : - / @) for clarity or example formats. |
| UI_Defaults | The UI_Defaults field specifies the pre-populated value that appears in a field when a new record is created. It helps streamline data entry, reduce user effort, and ensure consistency for frequently used values. | Type: Depends on the field type (string, number, boolean, date, or reference).Format:Match the data type of the field.For boolean fields, use true or false.Allowed characters:Alphanumeric and special characters valid for the field type. |
| UI_ReadOnly | The UI_ReadOnly field indicates whether a field is non-editable in the user interface. When set to true, users can view the field value but cannot modify it, ensuring that certain data remains controlled, consistent, and protected from accidental changes. | Type: Boolean (true / false). |
| UI_Mask | The UI_Mask field defines a formatting or input pattern applied to a field in the user interface to guide or restrict user input. It ensures data consistency, accuracy, and compliance by controlling how information is entered and displayed. UI masks are especially useful for fields that require specific formats such as phone numbers, social security numbers, dates, or identification codes. | Type: String (pattern or mask specification).Format:Use standard masking symbols based on field type (e.g., 9 for numeric, A for alphabetic, * for masked characters).May include separators or special characters to represent the desired format. |
| VAL_Required | The VAL_Required field specifies whether a field is mandatory when creating or updating a record. When set to true, the system enforces that a value must be provided for the field; leaving it empty will trigger validation errors. | Type: Boolean (true / false).Format:true: Field is mandatory.false: Field is optional. |
| VAL_Unique | The VAL_Unique field indicates whether a field must contain unique values across all records within an object. When set to true, the system enforces uniqueness, preventing duplicate entries for that field. | Type: Boolean (true / false).Format:true: Field values must be unique.false: Field values can be duplicated. |
| VAL_Min | The VAL_Min field specifies the minimum allowable value for a numeric or date field. It enforces data validation rules to prevent entry of values below a defined threshold. | Type: Depends on the field type. |
| VAL_Max | The VAL_Max field specifies the maximum allowable value for a numeric, date, or datetime field. It enforces data validation rules to prevent entry of values above a defined threshold, ensuring data accuracy, consistency, and compliance with business constraints. | Type: Depends on the field type |
| VAL_Regex | The VAL_Regex field defines a regular expression pattern used to validate the data entered in a field. Regex validation is commonly used for fields like email addresses, phone numbers, postal codes, or custom codes. | Type: String (regular expression pattern).Format:Must follow standard regex syntax supported by the platform.Include anchors (^ for start, $ for end) to enforce full-field validation.Escape special characters as required.Allowed characters:Alphanumeric characters, symbols, and regex meta-characters |
| IN_SyncDirection | The In_SyncDirection field specifies the data synchronization flow for a field when integrating Data Fabric objects with external systems. It determines how field values are updated during synchronization between Data Fabric and connected data sources. | Type: Enumerated string (controlled vocabulary).Allowed values (commonly supported sync directions):inbound: Data flows into Data Fabric from external systems.outbound: Data flows out of Data Fabric to external systems.bidirectional: Data flows in both directions, with conflict resolution rules applied.none: No synchronization is applied for this field. |
| IN_ConflictStrategy | The In_ConflictStrategy field defines the rule or policy applied when conflicting values are detected during data synchronization for a field. Conflicts typically occur in bidirectional or multi-source synchronization scenarios where the same field is updated in both Data Fabric and an external system. | Type: Enumerated string (controlled vocabulary).Allowed values (commonly supported strategies):latest_wins: The most recently updated value (based on timestamp) is retained.source_priority: A pre-defined system/source has higher authority; its value always wins.manual_review: Conflict is flagged for human intervention before resolution.merge: Both values are merged based on defined merge logic (for concatenated or list-based fields).discard_incoming: Retain existing Data Fabric value, discard incoming update.discard_existing: Accept incoming update, overwrite Data Fabric value. |
| IN_TimestampField | The In_TimestampField specifies the reference timestamp field used to determine the recency of data during synchronization or conflict resolution. This field is essential when multiple systems are updating the same data, as it provides a time-based benchmark to decide which update should be considered the most current. | Type: String (must map to a valid field name within the object schema).Format:Must directly reference an existing timestamp field in the object.Use camelCase or PascalCase depending on project-wide standards (e.g., lastModifiedDate or LastModifiedDate).No spaces or special characters (underscores may be allowed if consistent with system convention).Value scope:Should reference only fields of type = datetime/timestamp. |
| IN_SourceSystem | The In_SourceSystem field identifies the originating system for a field’s data during synchronization. It indicates which external or internal system is considered the authoritative source for the field value. This attribute is critical in multi-system integrations, where the same data element may exist across several platforms. | Type: String (enumerated or free-text depending on governance setup).Format:Use uppercase identifiers for system names (e.g., CRM, ERP, HRMS).If multiple words are needed, separate with underscores (e.g., SALES_FORCE, DATA_FABRIC_INTERNAL).Avoid spaces or special characters. |
| SR_Index | The SR_Index (Source Record Index) defines the index or ordering key of a field when multiple values are received from a source system for the same record. It is typically used in multi-valued or repeating field scenarios (e.g., multiple phone numbers, addresses, or identifiers for a single entity). |  |
| SR_Analyzer | The SR_Analyzer (Source Record Analyzer) defines the analysis engine or text-processing strategy applied to a field for indexing, searching, or semantic enrichment. It is primarily used for text-based fields to control how field values are tokenized, normalized, and indexed for search or downstream processing. | Type: String (enumerated or custom identifiers).FormatUse lowercase, underscore-separated values for analyzer names.No spaces or special characters/Must correspond to a predefined analyzer configuration in the indexing or search subsystem.Value scope: Common values include:keyword: Treats the entire field as a single token (useful for IDs, codes).standard: Default analyzer with basic tokenization and normalization.whitespace: Splits token on whitespaces only.lowercase: Normalizes all tokens to lowercase. |
| SR_Facet | The SR_Facet (Source Record Facet) determines whether a field can be used as a faceted attribute in search, filtering, or aggregation operations. Faceting enables users to group, filter, and navigate large datasets efficiently based on field values. | Type: Boolean (true / false). |
| SR_Boost | The SR_Boost (Source Record Boost) specifies the relative importance or ranking weight of a field when performing search or relevance scoring. By applying a boost value, certain fields can influence how search results are ordered, ensuring that matches on more significant fields are ranked higher than those on less important ones. | Type: Decimal (floating-point number).Format:Use numeric values with up to two decimal places (e.g., 1.0, 2.5, 0.75).Default boost is 1.0 (neutral weight).Higher than 1.0 increases importance; values between 0 and 1 reduce importance.Must not be negative. |
| SR_Stored | The SR_Stored (Source Record Stored) specifies whether the original field value should be stored in the index in addition to being indexed for search or analysis. | Type: Boolean (true / false). |
| Key | The Key field identifies whether a particular field should act as a primary identifier (or part of a composite identifier) for the object. A key field is critical for ensuring record uniqueness, indexing, and efficient retrieval. |  |
| Issues | The Issues field captures validation errors, warnings, or system-generated feedback related to the configuration or definition of a field | Type: Array or list of objects.Structure: Each issue entry contains at minimum:code: A short machine-readable identifier (e.g., MISSING_REQUIRED, INVALID_REGEX).message: A descriptive, human-readable explanation of the problem. |
