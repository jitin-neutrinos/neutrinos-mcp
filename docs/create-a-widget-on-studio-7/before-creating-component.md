### Recommendations and Best Practices

Before you start building a component, consider asking yourself the following questions:

- Are there existing components that I can reuse instead of creating a component?
- What is the purpose of the component?
- What packages will my component contain?
- What are the most important use cases, and how will my component help solve these use-cases?

Answering these questions will help you gain clarity on the functionality of the component and how the component should look when downloaded by other users.

#### Names and Descriptions

#### 

### 

Once your component is uploaded to [Neutrinos Store](/articles/concepts-publication/neutrinos-store), names and descriptions help users understand what is the goal of your component and how to use it. Names should be clear and clarify the functionality of the component. Therefore, make sure you give a clear name for your component and enter a proper description that describes the purpose of the component.

**Keep in mind these naming conventions:**

- Provide meaningful names for your component and for the attributes of the component. For example, use "Rich Text Editor", instead of "RTE") as the component name.
- Make sure that the name of the **Components Package** is your** <organization name>_components_package**.
- Prefix all your component files and folders with your organization name, followed by the component name. For example, all the default component files and folders provided by Neutrinos are prefixed with the keyword - **ndefault**, followed by the component name.
- Use PascalCase (for example, use "FirebaseNotification", instead of "Firebasenotification").
- Use event names that start with "On" (for example, "OnSubmit", instead of "Submit").
